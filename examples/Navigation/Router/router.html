Router

<juel-router> mounts the custom element of whichever route matches the current path, replacing what was there before. Routes are <juel-route path="…" element="tag-name"> children, checked in order — first match wins. Patterns support static segments, :param segments and a trailing *. The mounted element gets params (and rest for a wildcard) set before it connects.

mode picks where the path comes from: history (default — real URLs), hash (#/path) or memory (no URL, just the path property). In the URL modes, same-origin links anywhere on the page that match a route are handled without a page load (as in Blazor), and back/forward work; a memory router only handles links inside itself, and a link inside a router goes to that router first. router.navigate(path, { replace }) navigates from script.

A route can redirect="/new/:id", run a beforeEnter guard (sync or async; return false to block, a path to redirect), and lazy-load its element with module="url" or a load() function. The router has a navigating attribute while a guard or load is pending.

See it as a whole app

This page is a feature tour — a router halfway down a page of demos, with views a few lines long. Northwind Admin is the same router being an application: a sidebar and top bar outside it, real <juel-table> / <juel-chart> / <juel-tabs> inside its views, a sign-in guard on every route, a lazily loaded section and scroll-on-navigate="top".

Hash mode

Bound to this page's URL — watch the address bar, use back/forward, or reload on a route. The nav is ordinary <a href="#/…"> links; the "Grace" link in the bar above the router is outside it and works (and highlights) just the same. not-found names the element shown when no route matches. The external link and the target="_blank" link are left to the browser.

Guards and lazy loading: Old link is a redirect route (/people/:id → /users/:id). Admin's guard does a slow fake auth check and redirects to a sign-in view unless "Signed in" is ticked. Settings' guard blocks while "Lock settings" is ticked. Reports fetches its view's module on first visit; Broken lazy points at a missing module and fires route-error. A blocked or failed navigation leaves the URL where it was.

After each navigation the router sets aria-current on its links ("page" for the current route, "true" for a section containing it — Users while on Grace — styled in bold here), moves focus to the new view (focus-on-navigate="none" turns that off), and sets document.title from the route's title="User :id" — watch the tab (not-found-title does the same for the not-found view, which has no route element of its own). It also sets aria-busy while a guard or load is in flight and puts the new title into a hidden live region, so a screen reader is told where it has landed — announce-navigation="none" turns that off. A router that is the whole page can add scroll-on-navigate="top" to start each navigation at the top and restore scroll on back/forward; it's off here because this router sits halfway down a page.

History mode

        

            The default. Routes are real URLs, so the server has to answer every route URL with the
            app's page (a "rewrite to index.html" rule) — which this examples server
            doesn't do, so there's no live demo here. The app's prefix comes from
            <base href>, as in Blazor and Angular (or set base on the
            router to override it). Links are plain paths — relative ones resolve against
            <base> — and can sit anywhere, such as an app-shell nav outside the
            router.
        

        
<head>
    <base href="/app/">
</head>
<body>
    <nav>
        <a href="./">Home</a>
        <a href="users">Users</a>
    </nav>
    <main>
        <juel-router not-found="app-not-found" scroll-on-navigate="top">
            <juel-route path="/" element="app-home"></juel-route>
            <juel-route path="/users" element="app-user-list" title="Users"></juel-route>
            <juel-route path="/users/:id" element="app-user-detail" title="User :id"></juel-route>
        </juel-router>
    </main>
</body>

Memory mode

        

            mode="memory" never touches the URL — the router follows its
            path property alone, so several can live on one page. A new path always
            mounts a fresh element, so /users/1 → /users/2 re-runs the
            detail view's connectedCallback load. No not-found is set here,
            so an unknown path empties the outlet.
